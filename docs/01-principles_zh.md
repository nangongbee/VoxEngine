# VoxEngine 开发规则

开发规则、加功能的顺序、参考的库。

---

## 1. 要做成什么

一个开源的 TypeScript 语音交互引擎。

- 外面能接不同终端：ESP32 设备、网页麦，以后别的硬件。
- 里面用同一种「对话会话」处理。
- 下面能换说话方式：级联（识别 → 模型 → 合成）、端到端实时语音，以后混合。
- 模型厂商可以换，终端可以换，核心不动。

产品（人设、曲库、提醒等）用本仓库的公开 API 组装，不放进本仓库。

**产品拉着框架走。** 框架不靠设想去补功能：产品迁一个真实功能，缺什么口子补什么。

---

## 2. 简洁规则

1. **核心要小。** 核心只管一场对话：输入、打断、播放、事件。多一个功能先问能不能放到外层。
2. **一次只加一层。** 上一层能单独跑、能测、能讲清楚，再加下一层。
3. **每层能单独用。** 别人可以只用核心，或者只用适配器，或者跑完整服务。
4. **依赖只往下。** 外层可以用内层；内层不能知道外层是谁。
5. **只从入口导出。** 模块之间不引对方的内部文件。
6. **不为将来写代码。** 现在用不到的接口、配置、抽象，不写。
7. **默认能跑。** 例子装好就能跑通一段对话；密钥缺失时报清楚错，不静默失败。
8. **框架给机制，产品定策略。** 框架提供「能做到」：播放、打断、超时、取消、筛选的口子；「做成什么样」归产品：播什么、开放哪些工具、超时几秒、播完做什么。拿不准时问一句：换一个产品（车载、客服）还需要它吗？做法一样就进框架；需要但做法不同，框架只留口子；不需要就整个放产品。

## 3. 一点点丰富

能力按这个顺序加。前一步没稳，不进下一步。这是唯一的路线图。

| 步 | 加什么 | 做完能说明什么 | 版本 | 状态 |
|----|--------|----------------|------|------|
| 0 | 文档：分层、内部协议、规则 | 别人看得懂要做什么 | v0.1 | 完成 |
| 1 | 内部会话消息（适配器 ↔ 核心的合同） | 终端怎么接进来已经定死 | v0.1 | 完成 |
| 2 | 核心：会话、事件、下行播放、打断 | 一场对话有了骨架 | v0.1 | 完成 |
| 3 | 假终端适配器 + 测试 | 不用硬件也能跑通 | v0.1 | 完成 |
| 4 | 小智设备适配器 | BOX-3 能连上 | v0.1 | 完成 |
| 5 | 级联 Runtime（识别、模型、合成各一个 Provider） | 能真正对话 | v0.1 | 完成 |
| 6 | 网关：启动、关闭、连接表、事件日志 | 可以部署 | v0.1 | 完成 |
| 6.5 | Runtime 自报能力（实时转写、工具、打断） | 核心不再按「级联还是实时」猜 | v0.1 | 完成 |
| 7 | 实时 Runtime | 能切到端到端语音 | v0.1 | 完成 |
| 7.5 | 工具调用：媒体、超时、取消、设备工具筛选；「用户开口」的判断标准可配 | 讲故事这类工具能做 | v0.2 | 完成 |
| 7.6 | 产品口子：网关挂产品路由、每场会话选 Profile、播报入口、远程 MCP | 产品不用改框架就能搭起来 | v0.2 | 进行中，产品用到哪个做哪个 |
| 8 | 网页麦适配器 | 第二种终端证明适配层成立 | v0.3 | 未做 |
| 9 | 费用、可观测性、更多 Provider；流式识别、流式合成 | 开源时好用、好查；首包更快 | v0.3 | 未做 |
| 10 | 混合 Runtime：实时为主，工具收口到 Runtime，出错或工具过多时降级到级联 | 一份 Profile 三种说话方式 | 以后 | 未做 |

人设、曲库、提醒、纪要等放在产品侧，用上面的口子实现，不进框架。

## 4. 分层（一句话版本）

从大处看分三层：

| 层 | 是什么 | 在哪 |
|----|--------|------|
| 核心层 | VoxEngine：终端、会话、Runtime、Provider、工具调用、网关 | 本仓库 |
| 能力层 | 任务、送达渠道（音箱播报、飞书、网页）、工具来源、记忆。每个模块单独可选，只通过 `Tool`、播报入口、事件流接进来，核心不知道它们 | 现在没有；做异步任务时再定放哪 |
| 产品层 | 选择和组装：人设、开放哪些工具、结果推到哪、什么要确认 | 产品自己的仓库或应用 |

核心层内部：

```text
网关（启动、连接表、路由）
  ├ 终端适配器（小智、网页）
  ├ 核心（会话、事件、播放、打断、工具调用）
  └ Runtime（级联、实时）
      └ Provider（识别、模型、合成、实时语音、VAD）
```

适配器和核心之间的「内部会话消息」是第一个定下来的合同。

## 5. 技术约定

| 项 | 约定 |
|----|------|
| 语言 | TypeScript |
| 运行 | Bun 优先；核心不依赖 Bun 专有 API，Node 也能跑 |
| 校验 | 只在边界上校验（外部消息、厂商返回），手写；校验多到难维护时再引库 |
| 测试 | 每层都有测试；核心和适配器不碰真实网络也能测 |
| 网络 | WebSocket、HTTP；具体服务器实现只放在服务层 |
| 依赖 | 核心尽量零依赖；Provider 才依赖厂商 SDK 或 HTTP |
| 可观测 | 先有统一事件；OpenTelemetry 放到后面单独加 |
| 本地模型 | Python 能力（如 Silero、FunASR）作为独立服务，通过 Provider 接入 |

---

## 6. 开源要求

- 仓库里不出现私有 IP、密钥、个人姓名、家庭地址。
- 例子里的配置能被别人改成自己的厂商和终端。
- 中文提示词、面向具体产品的文案放在产品侧，不放核心。
- 每层有一页说明：负责什么、不负责什么、怎么单独用。
- 引用别人的设计要写明出处；不复制别人的代码，除非许可证允许并注明。
- 许可证：MIT。

## 8. 现在不做

- 插件加载器、热插拔
- 多用户账号体系
- 管理后台、Studio
- 网关的配置文件和命令行：网关是库函数，产品在代码里装配
- 能力层（任务、送达渠道、记忆）：等产品要做异步任务时再加
